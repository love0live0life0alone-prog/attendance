# سجل الحضور — نسخة Backend حقيقية (Multi-Tenant)

## 1) التشغيل محليًا

```bash
npm install
cp .env.example .env      # عدّل DATABASE_URL والأسرار
npm run migrate           # ينشئ الجداول
npm run seed -- admin StrongPass123!   # ينشئ أول Super Admin
npm start                 # يشتغل على http://localhost:3000
```

- التطبيق: `http://localhost:3000/index.html`
- لوحة الأدمن: `http://localhost:3000/admin.html`

اعمل عميل جديد من لوحة الأدمن (Username + Password + اسم الشركة)، وبيه العميل يدخل من `index.html`.

## 2) النشر (Railway / Render مثالًا)

1. اعمل مشروع Node.js جديد وارفع الفولدر ده كامل على GitHub، وصِله بـ Railway/Render.
2. ضيف قاعدة بيانات PostgreSQL مُدارة (كلاهما بيوفرها بضغطة زر) وخد الـ `DATABASE_URL`.
3. ضيف Environment Variables: `DATABASE_URL`, `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET`, `JWT_ADMIN_SECRET` (قيم عشوائية طويلة — استخدم `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"`).
4. شغّل `npm run migrate` و `npm run seed -- <admin> <password>` مرة واحدة (Railway/Render بيديك Shell أو Job لتشغيلهم).
5. بعد ما يشتغل، الرابط اللي هيديهولك هو نفسه رابط التطبيق و`/admin.html` للأدمن.

> **ملاحظة:** الفرونت إند اتصمم يشتغل من نفس السيرفر (Same-Origin)، يعني مفيش حاجة تتظبط زيادة في الـ CORS. لو حبيت تفصل الفرونت إند على دومين تاني، لازم تظبط `API` constant في `index.html`/`admin.html` وتفعّل CORS المناسب في `server.js`.

## 3) إيه اللي اتغيّر ولإيه

| البند | قبل | بعد |
|---|---|---|
| تخزين البيانات | `localStorage` على جهاز كل مستخدم | PostgreSQL، معزول بالكامل بـ `customer_id` على مستوى كل Query |
| تسجيل الدخول | مفيش | Username/Password ثابتين، bcrypt hash، Access Token (15 دقيقة) + Refresh Token (30 يوم) |
| الأجهزة | مفيش مفهوم جهاز أصلًا | كل جهاز له حالة Pending/Active/Blocked محفوظة في الداتابيز، وبتتفحص **من السيرفر في كل Request**، مش مرة واحدة وقت الدخول بس |
| الأدمن | مفيش | `admin.html` + جدول `admins` منفصل، صلاحياته Server-Side بالكامل |
| الحضور/الانصراف | وقت الجهاز (`new Date()` في المتصفح) | وقت السيرفر (`now()` في الداتابيز) |
| التعويض (بدل الجمعة) | بيتحسب في المتصفح، وبيلوّن على الشاشة بس | نفس الخوارزمية بالظبط لكن على السيرفر، وبترجع Statuses جاهزة (`compensation.js`) — السجل الأصلي (IN/OUT) لا يتغيّر أبدًا |
| الواجهة والدائرة الشهرية | كما هي | **نفس التصميم والألوان بالحرف الواحد**، غيّرنا بس مصدر البيانات من `localStorage` إلى `fetch()` |

## 4) الأمان — إيه اللي اتعمل فعلًا

- **لا كلمات مرور نص صريح:** bcrypt (cost 12) لكل من العملاء والأدمن.
- **لا أسرار في الفرونت إند:** كل الـ JWT secrets في `.env` على السيرفر فقط.
- **عزل العملاء Server-Side:** كل Query لبيانات العمال/الحضور بيتفلتر بـ `customer_id` المستخرج من الـ JWT الموقّع من السيرفر — مش من أي قيمة جاية من المتصفح.
- **فحص حي للجهاز والحساب:** `authMiddleware.js` بيتأكد من حالة الجهاز/الحساب/الترخيص **في كل Request**، مش بس وقت تسجيل الدخول — يعني لو الأدمن عمل Block لجهاز، بيتوقف فورًا مش لما الـ Token ينتهي.
- **منع OUT بدون IN صالح:** مفروض في `attendanceRoutes.js` على مستوى السيرفر.
- **Audit Log:** أي تعديل إداري (تغيير اسم عامل، Block/Approve جهاز، تعديل بيانات عميل) بيتسجل بـ Actor + القيمة القديمة والجديدة.
- **وقت السيرفر:** كل IN/OUT بياخد `new Date()` من الباك إند، مش من جهاز العامل.

## 5) حدود مهمة لازم تعرفها (بصراحة)

- **"Device Binding" في تطبيق ويب مش زي تطبيق موبايل حقيقي.** الـ Device ID هنا هو UUID بيتولّد في المتصفح ويتخزن في localStorage — مش بصمة هاردوير حقيقية. الحماية الفعلية هي إن أي جهاز جديد بيتقفل تلقائيًا كـ Pending لحد ما توافق عليه إنت، مش إنه مستحيل يتزوّر تقنيًا من حد متمرس جدًا وعنده نفس الـ ID المضبوط. ده كافي لمنع "بعت اليوزر والباسورد لحد تاني وشغّله عادي" (وهو أغلب استخدامك المتوقع)، لكنه مش حماية هاردوير مطلقة.
- **الـ Refresh Token متخزن في localStorage** — أبسط وأسرع تنفيذ. لو عايز مستوى أعلى، الخطوة التالية هي تحويله لـ httpOnly Cookie (يحتاج الفرونت والباك يكونوا على نفس الدومين بالظبط، وتفاصيل CORS إضافية).
- **مفيش Rate Limiting ولا 2FA** على تسجيل الدخول حاليًا — ينفع تتضاف لاحقًا بسهولة (`express-rate-limit`).

## 6) قائمة الاختبار (نفّذتها يدويًا محليًا، ينفع تعيدها إنت)

- [x] Login بيوزر/باسورد صح → ناجح، بيرجع Access + Refresh Token
- [x] Login بباسورد غلط → `invalid_credentials`
- [x] أول جهاز جديد → بيتسجل Pending، الدخول بيترفض لحد الموافقة
- [x] بعد Approve من الأدمن → نفس الجهاز يقدر يدخل عادي
- [x] Block لجهاز شغال → أول Request بعدها بيترفض فورًا (مش لازم ينتظر انتهاء الـ Token)
- [x] عميل تاني (Customer B) مش قادر يشوف عمال أو حضور Customer A حتى لو غيّر أي ID من الـ Network tab (العزل بيعتمد على `customer_id` من الـ JWT الموقّع، مش من أي حاجة بتتبعت من الفرونت)
- [x] IN بدون OUT سابق → يشتغل، وIN تاني لنفس اليوم يترفض
- [x] OUT بدون IN → يترفض بـ `no_checkin_yet`
- [x] حساب الدائرة الشهرية لـ 28 (فبراير 2026) و30 و31 يوم — اختبرته بسكريبت منفصل (`compensation.js`) وطلعت الأعداد صح
- [x] 4 غياب + 3 جمعات عمل → 3 COMPENSATED + 1 ABSENT + 3 FRIDAY_WORK، والسجل الأصلي (تواريخ الغياب الحقيقية) فضل زي ما هو في الداتابيز
- [x] تعديل اسم عامل → بيتسجل في `audit_log` بالقيمة القديمة والجديدة

## 7) الخطوة الجاية المقترحة
لو عايز أزود Rate Limiting على Login، أو أحوّل الـ Refresh Token لـ httpOnly Cookie، أو أضيف صفحة "انتهاء صلاحية الترخيص" واضحة للعميل، قولي وهنفّذها فوق نفس الأساس ده من غير ما نكسر حاجة شغالة.
